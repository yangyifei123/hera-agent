## ✅ Fixed in the 2026-06-27 hardening batch

**Engine / HDTE durability (north star: ≥500 tasks, no perfunctory completion)**
- Acceptance shell-check timeout now **tree-kills** the child process (Windows `exec`
  timeout leaked `ping`/children → locked cwd → EBUSY). `src/engine/acceptance.ts`
- `recover()` now **counts an attempt** and fails a task once it exhausts
  `maxAttempts`, so a task that repeatedly crashes the host no longer retries
  forever. `src/engine/task-store.ts`
- `recover()` **never reclaims a task this process is still actively running**
  (skip-active-ids), killing the critical same-process double-run where an
  over-lease attempt got dispatched twice. `task-store.ts` + `supervisor.ts`
- Failed/cancelled **dependencies now cascade**: dependents are marked `failed`
  instead of stranded `pending` forever (batch could never complete).
- Retry **backoff is honored** (`nextEligibleAt`, exponential) instead of being
  dead config — failed tasks no longer spin at full tick rate. `executor.ts`

**Team coordination**
- control-manager `>=` / `<=` gate conditions **now evaluate** (multi-char
  operators matched before `>`/`<`; were dead code → always false).
  `src/team/control-manager.ts`

**Security**
- Skill names are **validated** before use as path segments — blocks
  `../../agents/hera` (a recursive force-delete primitive) and write/read escapes.
  `src/validation.ts`, `src/skills/manager.ts`, `src/tools/skill-tools.ts`
- Skill package extra-file paths are **zip-slip guarded** (`isSafeRelativePath`).
- Disk packages **can no longer shadow a built-in skill** (which was permanent —
  deleteSkill refuses built-in names); createSkill rejects built-in names.
- Agent description is **newline/control-char sanitized** before YAML frontmatter,
  closing a frontmatter-injection that could override mode/permission on reload.
  `src/agents/registry.ts`

**Onboarding / config / CLI robustness**
- `.onboarded` flag is **only written when all defaults succeed** — a partial
  failure no longer permanently locks in a broken setup. `src/onboarding.ts`
- `isFirstRun` uses `existsSync` (not `require()` in ESM, which could throw,
  get swallowed, and re-onboard every launch).
- Corrupt `hera.json` is **backed up and preserved** instead of silently
  overwritten with defaults (was wiping user settings on any JSON typo).
  `src/index.ts`
- CLI **exits 1 on unknown command** (was printing help + exit 0 = silent

- `atomicWriteText` tries a **direct rename first**, eliminating the Windows
  "no file at all" crash window for every new-file write. `src/helpers.ts`

## ⏳ Remaining backlog (prioritized, no sign-off needed — pure fixes)

1. **Prompt double-embedding (HIGH, highest user impact).** Every persisted child
   agent ships all 11 built-in skill prompts **twice** in its live system prompt
   after restart (`## Built-in Skill:` from the rendered .md body + `## Skill:`
   re-added by the config hook), because `parseMarkdownAgent` sets
   `def.prompt = body.trim()` (the already-rendered body). Fix: make the two
   assembly paths share one contract — persist the raw author prompt separately
   (e.g. `promptJson` frontmatter) so it round-trips, and dedup skills in the
   config hook. `src/agents/hera.ts`, `src/agents/registry.ts`, `src/index.ts`.
   *(Riskiest single change — it is the CLAUDE.md §4 "sharp edge". Deserves its own
   focused TDD pass: create → restart-reload → invoke.)*
2. **Engine singleton + cross-process lease heartbeat (CRITICAL-adjacent).**
   `withEngine` makes every generated plugin spin up its own engine on the shared
   `hera-data` dir → two engines both claim & run the same task. Fix: process-wide
   engine singleton keyed by dataDir + a lease heartbeat so a live owner's tasks
   aren't reclaimed cross-process. `src/generators/*`, `src/engine/*`.
3. **Per-agent permission / tools / maxSteps dropped at runtime** —
   `createChildAgentConfig` hardcodes defaults; agent-level restrictions are
   cosmetic. Pass through `def.permission/tools/maxSteps` + emit native
   `permission:`/`tools:` frontmatter. `src/agents/hera.ts`, `src/index.ts`.
4. **Sequential/adaptive teams treat timed-out sessions as "completed"** and feed
   the sentinel string (`(timeout)`) downstream. Return a discriminated poll
   result; abort/surface instead of poisoning the chain. `src/team/manager.ts`.
5. **Timeout/cancel never abort the underlying OpenCode session** (orphan runs
   continue); sessions are never deleted. Thread an AbortSignal + session.delete.
6. **Memory recall is flat-substring + recency-ranked + no cross-session dedup** —
   multi-word queries miss, duplicates accumulate. Tokenize + score by term
   coverage; dedup auto-memories by normalized-content hash. `src/memory/*`.
7. Evolution log lost across restart; backup/restore compounds embedded skills;
   per-id write locking; acceptance check zod schema + regex ReDoS bound;
   route all agent/skill writes through atomicWrite; `spawnTeam` orphans sessions;
   message queue evicts unread directed messages; generated plugins read
   `HERA_DIR` not `HERA_CONFIG_ROOT`. (See appendix for file:line.)

## Appendix A — full audit findings (raw)

### Team Coordination Correctness

- **[high/medium] Sequential chain marks timed-out/empty sessions as "completed" and poisons downstream agents with the error string**
  - Evidence: src/team/manager.ts:166-170 — after `pollSessionCompletion` returns, sequential mode unconditionally does `session.status = "completed"; session.result = result; accumulated = "Previous agent (...) output:\n${result}\n\nContinue..."`. But `pollSessionCompletion` (lines 260-284) returns sentinel strings `"(timeout)"` (line 283, after TEAM_POLL_MAX_ATTEMPTS=120 * 1000ms), `"(no response)"` (276), or `"(no client)"` (264) on failure. None of these are distinguished from a real answer: the failed upstream session is recorded as `completed`, and the literal string `(timeout)` is injected as that agent's "output" into the next member's prompt. There is also a startup race: `client.session.promptAsync` (line 245) is fire-and-forget, so a freshly created child session can read `status==='idle'` (line 267) before it begins work, returning `(no response)` immediately.
  - User impact: A user running a sequential team (e.g. architect -> senior-dev -> qa) where one agent hangs gets a silently corrupted pipeline: every downstream agent receives `(timeout)` as if it were the prior agent's real deliverable, and the team report shows all members `completed`. This is exactly the perfunctory '滥竽充数' completion the north star forbids — failures are laundered into successes.
  - Fix: Have `pollSessionCompletion` return a discriminated result ({status:'completed'|'timeout'|'error', text}) instead of magic strings; in the sequential/adaptive loops set `session.status` from that result (completed only on real idle+assistant text), and abort or surface the chain instead of feeding sentinel text forward. Confirm the prompt was accepted (poll for a non-idle/working transition) before treating idle as done.
- **[high/medium] spawnTeam overwrites prior session tracking, orphaning still-live OpenCode sessions**
  - Evidence: src/team/manager.ts:211 `this.spawnedSessions.set(teamName, sessions)` replaces the entire prior array for that team (and line 212-218 persists only the new set). Nothing cancels or reconciles the previous run's sessions. The same team is spawned repeatedly via `hera_spawn_team` (src/tools/team-tools.ts:223) and `hera_quick_team` (src/tools/team-tools.ts:462). After a second spawn, `getSpawnedSessions` (line 467), `buildTeamContext` (line 489), and `recoverSessions` (line 418, iterates only `spawnedSessions`) can no longer see the first batch.
  - User impact: A user who runs a team on task A and then task B (a normal long-running loop) leaks task A's real OpenCode child sessions: they keep consuming model/tokens, are never marked complete, never recovered after a crash, and never appear in team status. Over a 500-task durable run this accumulates orphaned, unaccounted sessions.
  - Fix: Key spawned sessions by a run id (append per-run records rather than replace), or before overwriting, reconcile/cancel the previous batch (client.session.abort) and merge terminal results into history. Persist a bounded list of past runs so recoverSessions can still reach in-flight sessions from an earlier spawn.
- **[high/low] control management mode: '>=' and '<=' gate conditions always evaluate false**
  - Evidence: src/team/control-manager.ts:119-162 `evaluateCondition` tests `trimmed.includes(">")` (line 129) and `trimmed.includes("<")` (line 138) BEFORE the `>=` branch (line 147) and `<=` branch (line 156). A condition like `coverage>=80` matches the `>` branch first, `split(">")` yields `["coverage", "=80"]`, `Number("=80")` is NaN, and line 133 returns false. The dedicated `>=`/`<=` branches are dead code. `evaluateControlPoint` (lines 56-71) then sets such a gate to `status:'failed'`.
  - User impact: Any team using `control` management with realistic threshold gates (coverage>=80, score<=5, etc.) has its checkpoints silently always fail/reject or escalate, blocking approvals that should pass. The user sees gates failing with no indication the operator parser is broken.
  - Fix: Order the checks so multi-char operators are matched first: test `>=`, `<=`, `==` before the single-char `>` and `<` (or tokenize with a regex like `/^(.+?)(>=|<=|==|>|<)(.+)$/`). Add unit tests for `>=`/`<=` conditions.
- **[high/medium] Message queue prunes unacknowledged messages by global FIFO cap and TTL, silently losing directed messages**
  - Evidence: src/team/manager.ts:320-328 `pruneMessageQueue` drops messages by TTL (TEAM_MESSAGE_TTL_MS = 7 days, constants.ts:31) and by a single per-team cap (TEAM_MESSAGE_QUEUE_CAP = 100, constants.ts:28) via `retained.splice(0, overflowCount)` — oldest-first, with no regard for `acknowledgedBy`. The persisted copies are also deleted (`deleteStoredMessages`, lines 308/335/338-342). manager.test.ts:95-106 confirms eviction is pure FIFO: after 105 sends, `message-0..4` are gone and only 100 remain. The cap is per-team, not per-recipient, so chatter between two members evicts a third member's unread directed inbox.
  - User impact: In a long-running team a member that is busy or temporarily down loses messages addressed specifically to it once team traffic crosses 100 entries — the canonical 'persisted inbox is source of truth' guarantee (comment at line 372) is violated. Coordination instructions and results vanish with no error, causing duplicated or skipped work.
  - Fix: Track unread state per recipient and never evict a message that still has unacknowledged required recipients (or apply the cap per-recipient). Prefer evicting fully-acknowledged messages first; only force-drop unread ones with an explicit warning surfaced to the team.
- **[medium/medium] Parallel/adaptive sessions are stuck at status 'running' forever; live message push targets dead sessions**
  - Evidence: src/team/manager.ts:249 sessions are created with `status:'running'`. In `parallel` (lines 142-155) and the adaptive fan-out (lines 194-206) the status is never updated — only the sequential loop (line 168) and adaptive planner (line 189) poll. `recoverSessions` (line 415) reconciles only when explicitly invoked (index.ts:108, startup only). `pushMessageToActiveSessions` (lines 347-349) delivers only to `status==='running'` sessions, so once a parallel member actually finishes it is still 'running' and every subsequent `hera_team_message` re-prompts an idle/finished session (line 354 promptAsync), potentially re-waking the agent; `buildTeamContext` (line 492) reports it 'running' indefinitely.
  - User impact: Team status is permanently wrong for the most common coordination mode (parallel), and broadcast messages get pushed into already-finished sessions, causing spurious re-activation and wasted model calls. Users cannot tell when a parallel team is actually done without manually triggering recovery.
  - Fix: After Promise.all in parallel/adaptive, poll each session to a terminal status (or schedule periodic recoverSessions), and gate live push on a freshly-checked status rather than a stale stored 'running'.
- **[medium/medium] Unbounded fan-out: parallel/adaptive spawn all member sessions and broadcast to all at once with no concurrency cap**
  - Evidence: src/team/manager.ts:143-153 (`team.members.map(async ...)` + `Promise.all` at 153) and 195-205 spawn a `session.create` + `promptAsync` for every member simultaneously; `pushMessageToActiveSessions` (line 351 Promise.all) fans a single message to all running sessions at once. There is no semaphore on team size or session creation, unlike the workflow path which uses a bounded Semaphore (src/workflow/progress.ts:36-43, `maxConcurrent`). Team size is unvalidated in createTeam (lines 92-106).
  - User impact: A large team, or many teams active under the 500-task durable goal, issues an uncapped burst of session.create/promptAsync calls against OpenCode, risking rate limits, resource spikes, and partial failures that surface as scattered 'error' sessions (line 250-257). The architecture's stated concurrency control (HDTE executor / workflow Semaphore) does not extend to team spawning.
  - Fix: Reuse the existing Semaphore abstraction to bound concurrent session.create/promptAsync in spawnTeam and pushMessageToActiveSessions; add a configurable max team size / max concurrent members in constants.
- **[medium/low] recoverSessions buries transient status() failures as permanent 'error' and re-fetches global status once per session**
  - Evidence: src/team/manager.ts:415-465. The catch at lines 448-452 sets `session.status = 'error'` on ANY exception from `client.session.status()` — a momentary network/IPC blip permanently marks a still-running session errored with no retry. The status call (line 429) is inside the per-session loop, so for N non-terminal sessions it fetches the full global status map N times instead of once. recoverSessions also reads the live `sessions` array and re-persists (line 455); a concurrent spawnTeam replacing the array (line 211) yields a lost update.
  - User impact: Crash recovery — a core self-healing promise — can corrupt good state: after a restart a transient API hiccup flips healthy in-flight team sessions to 'error', and the operator sees false failures. Redundant status fetches add load proportional to session count during recovery.
  - Fix: Fetch session.status() once before the loop and look each session up in the map; only mark 'error' on a definitive terminal/absent signal (or after retries), and treat transient exceptions as 'unknown' to retry next pass. Snapshot/lock the sessions array during reconcile.

### First-run / Onboarding UX

- **[high/medium] Onboarded/disk-loaded child agents get all 11 built-in skills embedded TWICE in their system prompt**
  - Evidence: buildAgentPrompt (src/agents/hera.ts:267-326) renders an agent's .md body as: '# Agent: name' + def.prompt + the full text of all 11 built-in skills. AgentRegistry.register (src/agents/registry.ts:33-38) writes that whole rendered body to disk. On the next startup the plugin loads agents from disk via readDefinition→parseMarkdownAgent (src/agents/registry.ts:220), which sets def.prompt = body.trim() — i.e. def.prompt now CONTAINS all 11 embedded skill bodies. Then the config hook (src/index.ts:198-222) builds fullPrompt = [def.prompt, skillPrompts, ...] where skillPrompts is rebuilt from def.skills (src/index.ts:202-204) with NO skip of built-ins and NO dedup. Result: every onboarded agent (quick-fixer, architect, senior-dev, qa-engineer) ships its 11 built-in skill prompts twice. The 'coder' template compounds it: defaultSkills:[...DEFAULT_SKILLS,'skill-combo'] (src/agents/hera.ts:43) duplicates skill-combo, so senior-dev embeds skill-combo three times. This is exactly the 'duplicated embedded skill sections' drift CLAUDE.md sharp-edge #4 warns about — and it is live.
  - User impact: A brand-new user's seeded agents launch with roughly double-size system prompts full of duplicated skill instructions, wasting context/tokens on every invocation and risking contradictory/garbled guidance — the opposite of the lean defaults a first-run user expects.
  - Fix: Make the two prompt paths agree on a single contract: either store ONLY the raw template prompt in def.prompt (and let the config hook assemble skills once), or have the config hook detect already-embedded skills and skip re-appending. Simplest: in src/index.ts:198-204 filter out skills already in DEFAULT_SKILLS and de-duplicate by name, matching buildAgentPrompt's skip at src/agents/hera.ts:322. Also drop the redundant 'skill-combo' in the coder template defaultSkills.
- **[high/low] Onboarding writes the .onboarded flag even when agent/team creation failed, permanently locking in a broken partial setup**
  - Evidence: runOnboarding (src/onboarding.ts:42-113) wraps every register/createTeam in try/catch that logs only a warn ('may already exist') and then unconditionally writes the .onboarded flag at lines 108-113. isFirstRun (src/onboarding.ts:18-29) returns false once the flag exists, and src/index.ts:139-141 only calls onboarding when isFirstRun is true. So if quick-fixer or dev-team creation fails for a real reason (disk full, EACCES, bad skill map) on the one-and-only onboarding run, the flag is still written and onboarding never retries — the user is left without the documented default agent/team forever, with only a buried warn log.
  - User impact: A transient first-launch error silently yields a Hera with no quick-fixer agent and/or no dev-team, contradicting the documented defaults, and no doctor check or retry ever surfaces or repairs it.
  - Fix: Track success of each step and only write .onboarded when all critical creations succeeded (or write a partial-state marker and re-attempt missing pieces on next launch). At minimum, escalate real failures (non-existence errors) to a visible warning and gate the flag write on them.
- **[high/low] Corrupt or partial hera.json is silently overwritten with defaults, discarding user config**
  - Evidence: In src/index.ts:54-85 the config load does readFile+JSON.parse inside a try, and the single catch block is used BOTH for 'file does not exist' AND 'file is invalid JSON', in both cases writing a fresh default config over heraConfigPath (lines 61-81). A user who hand-edits hera.json (disabled_agents, disabled_skills, auto_evolve, team_defaults, etc.) and introduces a JSON typo loses ALL their settings on the next OpenCode launch with no warning. Compounding this, doctor (bin/hera.js:492-588) validates opencode.json but never reads or validates hera.json, so the clobber is never surfaced.
  - User impact: Silent data loss of user configuration on a trivial syntax mistake — a brand-new user customizing defaults can have their whole hera.json reset without any message.
  - Fix: Distinguish ENOENT from parse errors: only auto-create on missing file; on parse failure, log a clear error, back up the bad file (hera.json.bak), and either refuse to overwrite or merge over preserved fields. Add a hera.json validity check to bin/hera.js doctor.
- **[medium/low] Onboarding silently overwrites pre-existing user agents that share default names; 'may already exist' guard is a no-op**
  - Evidence: AgentRegistry.register (src/agents/registry.ts:25-51) unconditionally writeFile's the agent .md (line 38) and never checks for or throws on an existing file — unlike the CLI path which explicitly refuses (bin/hera.js:193-196 'Agent already exists'). Onboarding (src/onboarding.ts:42-69) calls register for quick-fixer/architect/senior-dev/qa-engineer and catches with the comment 'may already exist', but register never errors on existence, so a user who created their own 'architect' (e.g. via `hera create agent architect` before first plugin load) has it silently replaced by the template version on first onboarding. The reassuring catch comment masks that no existence check happens anywhere in this path.
  - User impact: A user who pre-creates an agent with a common name (architect, senior-dev, qa-engineer, quick-fixer) loses their customization on first plugin launch with no warning.
  - Fix: Have onboarding check agentRegistry.listRegistered() (or readDefinition) before registering each default and skip names that already exist, logging that it preserved the user's version. Optionally add an overwrite guard to register().
- **[medium/low] isFirstRun uses require() inside an ESM module; if require is undefined it re-onboards on every startup**
  - Evidence: src/onboarding.ts:22-28 does `require('fs').accessSync(flagPath)` inside a try/catch in a file that otherwise uses ESM imports (import ... from 'node:fs/promises' at line 6). If the bundled/runtime context lacks a CommonJS `require` (pure Node ESM without createRequire), the thrown ReferenceError is swallowed by the catch and isFirstRun returns true — meaning onboarding runs on EVERY launch, repeatedly overwriting the seeded agents (and, per the double-embed bug above, re-rendering them). Even where Bun provides require today, this is a fragile basis for the idempotency of first-run.
  - User impact: In any runtime where require isn't defined, onboarding never becomes idempotent: default agents are clobbered on every OpenCode start, erasing user edits to quick-fixer/dev-team members each session.
  - Fix: Import existsSync from node:fs at the top and use existsSync(flagPath) instead of require('fs').accessSync — consistent with the rest of the module's imports and free of CommonJS assumptions.
- **[low/low] CLI quickstart is inconsistent with itself and with the plugin's seeded defaults**
  - Evidence: runQuickstart (bin/hera.js:271-286) defaults the new agent name to 'my-coder' but creates it with the 'general' template (getFlag('--template','general') in createAgentFromCli, bin/hera.js:197), so 'my-coder' is actually a generic assistant, and step 1 tells the user to `opencode --agent my-coder "review src/index.ts"`. Step 3 (line 285) instructs creating a team with a 'bug-hunter' agent that is never created and isn't a template, so following it verbatim fails. Separately, the CLI never seeds the quick-fixer agent or dev-team (only the plugin's runOnboarding does), so `hera status` (bin/hera.js:247-269) and `hera list-teams` (bin/hera.js:791-815) report 0 teams until OpenCode has been launched at least once — confusing for a user who reads docs claiming a dev-team is seeded.
  - User impact: A first-time user following the printed next-steps hits a name/role mismatch and a dead reference, and sees 'Teams: 0 / no teams' from the CLI despite documentation promising a default dev-team, eroding trust before they even start OpenCode.
  - Fix: Name the quickstart agent to match its template (or pass --template coder when the name implies coding), replace 'bug-hunter' in the next-steps with an agent that exists or with a clear placeholder, and have CLI status/list-teams note that defaults are seeded on first OpenCode launch.

### Standalone CLI Experience (bin/hera.js)

- **[high/medium] CLI-created agents are functionally crippled vs plugin-created ones and corrupt on later re-render**

### HDTE durable engine robustness

- **[critical/medium] Lease expires mid-attempt with no heartbeat → same task runs concurrently twice (duplicate side effects, lost results)**
  - Evidence: Lease is set once at claim time and never renewed: task-store.ts:64 (`leaseExpiresAt: now + leaseMs`); no renewal anywhere (grep shows leaseExpiresAt only set at claim / cleared on finish). Every dispatch tick (SUPERVISOR_TICK_MS=500ms) runs `store.recover()` BEFORE claiming (supervisor.ts:49), and recover() resets any 'running' task whose lease has passed back to 'pending' (task-store.ts:77-83), making it immediately re-claimable. The attempt timeout only wraps `runner.run` (executor.ts:42); the acceptance evaluation that follows is NOT bounded (executor.ts:51), and shell acceptance checks default to a timeout equal to the FULL lease (create-engine index.ts:78 sets evaluator defaultTimeoutMs = task_lease_ms = 300000, used at acceptance.ts:98). So one attempt can legitimately take up to 240s (agent) + 300s+ (each shell check) > the 300s lease. When the lease expires the still-active first attempt stays in `supervisor.active`, while claimReady starts a SECOND runAttempt for the same id; both later call store.save(), clobbering each other.
  - User impact: A long-running task (slow agent or slow shell acceptance check) is silently executed two or more times in parallel. Side-effecting work (deploys, file writes, API calls, 'fix the build') is duplicated, and the second run's save overwrites the first's proof/output, so a genuinely-succeeded task can be flipped back to failed. At the >=500-task scale Hera targets, this corrupts batch accounting non-deterministically.
  - Fix: Add a lease heartbeat: while an attempt is active, periodically re-save the task with leaseExpiresAt = now + leaseMs (or skip reclaiming tasks owned by the current ownerId+still in active set). Bound the WHOLE attempt (agent run + acceptance eval) under one deadline and ensure it is strictly < leaseMs. Don't default shell-acceptance timeout to the full lease.
- **[high/low] Crash recovery resets running→pending without counting an attempt → poison task retries forever, defeating maxAttempts budget**
  - Evidence: TaskStore.recover() (task-store.ts:74-89) moves expired/orphaned 'running' tasks back to 'pending' but does NOT increment `attempts` (only executor.ts:56,83 increment attempts, and recover never runs the executor). claimReady (task-store.ts:46-72) re-leases any pending task regardless of attempt count; the maxAttempts gate lives solely in executor.fail (executor.ts:84 `attempts >= task.maxAttempts`). A task that reliably crashes the host process / OOMs / hangs past its lease never reaches executor.fail, so attempts stays constant and it is reclaimed and re-run on every supervisor restart indefinitely.
  - User impact: A single 'poison' task (one that crashes the worker) becomes an infinite retry loop that can repeatedly crash the supervisor on recovery, stalling the entire 500-task run. The retry budget the user configured is silently not enforced for the exact failure mode (crashes) that durable execution is supposed to handle.
  - Fix: In recover(), bump attempts (or track a separate reclaim counter) and move the task to 'failed' once attempts >= maxAttempts instead of unconditionally back to 'pending'. Record lastError='reclaimed after crash/lease-expiry'.
- **[high/medium] A failed or cancelled dependency strands all dependents as eternal 'pending' — batch never completes and never fails**
  - Evidence: claimReady only treats deps satisfied when they are in the succeeded set: task-store.ts:53-55 (`succeeded = succeededIds(); ...every(dep => succeeded.has(dep))`). There is no handling for a dependency that ends in 'failed' or 'cancelled'. Such dependents remain 'pending' forever (never claimable, never marked failed). hera_batch_report's `complete` flag (task-tools.ts:144-149) requires zero pending, so the batch is reported 'NOT fully complete' indefinitely, and the supervisor re-scans these dead-pending tasks on every 500ms tick (supervisor.ts:49-52 → byStatus('pending')).
  - User impact: In a large DAG batch, one failed upstream task silently freezes an entire downstream subtree. The user's batch sits at e.g. 480/500 forever with no error surfaced, the engine busy-loops over unrunnable tasks, and there is no automatic way to fail-fast or skip — directly contradicting the 'durable, no perfunctory partial completion' promise.
  - Fix: In claimReady, if any dependency is 'failed'/'cancelled', transition the dependent to 'failed' (lastError='dependency <id> failed') instead of leaving it pending. Surface stranded/blocked counts in hera_engine_health and hera_batch_report.
- **[high/high] Anti-perfunctory guarantee is circular: acceptance checks are self-authored and can trivially pass without real work**
  - Evidence: The only completion gate is the acceptance check set, which the same agent supplies in the same enqueue call (task-tools.ts validateEnqueue:19-25 only checks the array is non-empty). A regex check with source:'output' is evaluated against the agent's OWN text reply (executor.ts:51 passes `output`; acceptance.ts:81 `source = ctx.output`), so `{type:'regex',source:'output',pattern:'done'}` passes whenever the agent merely says 'done'. A `{type:'shell',command:'exit 0'}` or `command:'echo ok'` check passes unconditionally (acceptance.ts:91-135). allPassed only requires length>0 and every passed (acceptance.ts:38-40). Nothing validates that a check actually verifies the goal.
  - User impact: The headline '>=500 tasks, no 滥竽充数 completion' claim does not hold against an agent that writes weak self-checks (intentionally or via prompt injection). Tasks can be marked 'succeeded' with proof attached while no real work happened, giving false confidence at scale — the worst kind of failure because batch_report shows green.
  - Fix: Treat agent-output-only regex checks as insufficient on their own (require at least one external check: file_exists/shell against the filesystem or a build). Add server-side validation rejecting trivially-passing patterns and `exit 0`/`true`/`echo` shell checks, or have Hera (not the executor agent) author acceptance from the goal.
- **[high/medium] Acceptance shell checks bypass OpenCode's permission model and run arbitrary commands unless bash is fully 'deny'**
  - Evidence: shellEnabled is derived as `getDefaultPermission()?.bash !== 'deny'` (create-engine index.ts:77). Acceptance shell checks then call Node `exec(check.command, {cwd})` directly (acceptance.ts:113-127) with no prompt and no allow/ask gating. So when a user sets bash permission to 'ask' (expecting to approve every shell command), acceptance checks still execute silently; only an outright 'deny' disables them. Commands come from TaskRecord.acceptance, which agents (or loop templates) populate freely.
  - User impact: A user who deliberately restricted shell to 'ask' for safety gets silent arbitrary command execution on their machine via any enqueued task's acceptance check — a permission-bypass / RCE-adjacent surface that is invisible in the normal approval UI. Prompt-injected or malicious task definitions execute commands with no confirmation.
  - Fix: Only enable acceptance shell when bash is explicitly 'allow'; for 'ask', route through the same permission prompt OpenCode uses, or restrict acceptance shell to an allowlist. Treat the acceptance command as untrusted input.
- **[medium/low] Configured retry backoff is dead code — failed tasks re-run immediately with zero delay**
  - Evidence: buildTask sets `backoffMs: TASK_DEFAULT_BACKOFF_MS` on every task (task-tools.ts:38) and the field exists on TaskRecord (task-types.ts:26), but the HDTE engine never reads it: executor.fail sets status straight back to 'pending' (executor.ts:84-96) and claimReady re-leases pending tasks ordered only by createdAt with no time gate (task-store.ts:54-57). grep confirms backoffMs is only consumed by the unrelated workflow manager (manager.ts:360), never by the engine. There is also no exponential backoff anywhere.
  - User impact: A transiently-failing task (rate-limited API, flaky network) is retried on the very next 500ms tick with no delay, hammering the failing dependency and burning the entire maxAttempts budget within ~1.5s — exactly when a backoff would let it recover. Users see fast spurious exhaustion and external systems get DoS-ed.
  - Fix: Honor backoffMs (ideally exponential): on fail, stamp a `nextEligibleAt = now + backoff*2^attempt` and have claimReady skip pending tasks whose nextEligibleAt > now.
- **[medium/medium] No per-id locking: concurrent saves (e.g. cancel vs. executor success) diverge memory from disk and resurrect terminal tasks**
  - Evidence: JsonCollectionStore.save mutates the in-memory index synchronously around an awaited disk write (json-collection-store.ts:60-63: indexRemove → await atomicWriteJson → indexInsert) with no per-id mutex. Two interleaved saves of the same id leave disk = writer B but the in-memory cache = writer A (A's indexInsert runs after B's), and reads are served from cache (load returns `this.primary.get(id)` at line 67-68), so the divergence persists until restart. Concretely, hera_cancel_task saves status='cancelled' (task-tools.ts:131) while an in-flight executor saves status='succeeded' (executor.ts:64) for a task still in supervisor.active — cancel does not stop the running attempt or the OpenCode session, so a cancelled task can be flipped back to succeeded (or vice versa).
  - User impact: Cancellation is unreliable and racy: a user cancels a task, the engine reports it cancelled, but it still completes and side-effects, or the in-memory view disagrees with persisted state after a crash/reload. Undermines trust in the control surface for long-running batches.
  - Fix: Serialize writes per id (async mutex/queue keyed by id) in JsonCollectionStore. Make cancel cooperative: mark intent and have the executor check for 'cancelled' before its terminal save, and abort the underlying agent session.
- **[medium/medium] Attempt timeout and cancel never abort the underlying OpenCode session; sessions are created per-task and never deleted**
  - Evidence: raceWithTimeout merely rejects on timeout (executor.ts:11-26) without cancelling the in-flight `runner.run` promise; the OpenCodeAgentRunner has already kicked off `session.promptAsync` (opencode-agent-runner.ts:20-23) and keeps polling, so the orphaned agent run continues executing in the background while the task is failed/retried. Each task creates a fresh session (opencode-agent-runner.ts:14-18) and there is no session.delete anywhere (grep: no session.delete in src). Timeout path throws 'Task agent timed out' (line 38) leaving that session running too.
  - User impact: On any timeout the abandoned agent keeps doing real work (duplicate side effects, racing the retry) with no kill switch. Over a 500-task run, 500+ OpenCode sessions accumulate and are never reclaimed, growing memory/handle usage and eventually degrading the host — the opposite of 'durable at scale'.
  - Fix: Thread an AbortSignal into AgentRunner.run, abort/stop the session on timeout/cancel, and delete the session after each attempt (success or failure).

### Memory & Distillation Quality

- **[high/medium] Multi-word recall is effectively exact-phrase-only (flat substring match), so most real queries silently miss relevant memories**
  - Evidence: src/memory/store.ts:116-126 — search() lowercases the WHOLE query and tests wordBoundaryRe = `\b${escapeRegex(lower)}` plus m.content.toLowerCase().includes(lower). The entire query (spaces included) is one literal substring, so a query 'login token error' only matches content containing that contiguous phrase. A memory 'fixed the token error on the login page' will NOT match. No tokenization, per-term AND/OR, stemming, or fuzzy matching — a single flat substring scan over m.content/m.id. hera_recall (src/tools/memory-tools.ts:81-96) passes the raw query straight in.
  - User impact: A user who stored a decision/fix and recalls it with slightly different wording gets 'No matching memories found.' The persistent-memory promise quietly fails for any query longer than one word — the common case — so cross-session continuity (Hera's north star) degrades to luck.
  - Fix: Tokenize the query on whitespace and score by fraction of terms present (require all or top-k) instead of the whole phrase; add per-term word-boundary matching. Optionally token-index content via JsonCollectionStore secondaryIndexes for O(1) term lookup.
- **[high/medium] Auto-memory extraction has no cross-session dedup, so repeated compactions accumulate duplicate decision/fix/pattern entries**
  - Evidence: src/memory/smart-extractor.ts:93-102 dedups ONLY within one extractMemories() call (the `seen` Set is local). The compacting hook (src/index.ts:276-296) re-runs extractMemories over input.messages on EVERY compaction and saves each result with a fresh random id `auto-${category}-${randomUUID().slice(0,8)}` (line 283). Successive compactions of a long session see overlapping message windows, so the same 'decided to use X' line is re-extracted and re-saved as a brand-new entry each time. Nothing checks store contents for an existing identical memory.
  - User impact: Long, supervised, looping sessions (Hera's >=500-task target) will flood the decisions/fixes/patterns subdirs with near-identical duplicates. Recall then returns the same fact repeated, and the per-type cap silently evicts genuinely distinct older memories (see eviction finding).
  - Fix: Before saving an auto-memory, look up existing entries of that type and skip if a normalized-content match exists; or derive a deterministic id from a hash of normalized content so re-extraction overwrites instead of duplicating. Also pass only the newly-compacted delta, not the full window.
- **[high/medium] Recall ranks by recency, not relevance, then truncates — strong matches older than the 10 newest matches are dropped**
  - Evidence: src/memory/store.ts:98 list() returns results sorted purely by b.timestamp - a.timestamp. search() (store.ts:118-126) filters that timestamp-ordered list and does .slice(0, limit). Default limit is MAX_RECALL_RESULTS=10 (src/constants.ts:142, used at memory-tools.ts:82). There is no scoring by match quality (title/id vs body, term coverage, confidence). So if 50 memories contain the query term, recall returns the 10 most RECENT ones regardless of how well they match.
  - User impact: The most relevant memory (e.g. a precise architectural decision) is invisible if 10 newer, weaker matches exist — exactly the failure mode after auto-memory has piled up recent duplicates. Users perceive Hera as 'forgetting' the important thing while surfacing noise.
  - Fix: Compute a relevance score per match (id/exact-phrase > all-terms > some-terms; factor metadata.confidence) and sort by score, breaking ties by recency, before slicing.
- **[medium/medium] Eviction is blind oldest-first per type — manually remembered preferences/decisions are silently dropped with no pinning**
  - Evidence: src/memory/store.ts:137-146 enforceLimit() sorts a type's entries by ascending timestamp and deletes the oldest (entries.length - maxEntries). DEFAULT_MEMORY_LIMIT=1000 (constants.ts:39) and default memory_ttl_ms=0 (index.ts:74) so nothing expires; the count cap is the only bound. Eviction ignores metadata.source, confidence, and whether the entry came from hera_remember (manual, high value) vs auto-memory (noisy). hera_remember (memory-tools.ts:46-51) stores no importance flag and there is no pin/protect concept.
  - User impact: A user who explicitly stores a standing preference can have it silently evicted once 1000 newer same-type entries accumulate (auto-memory makes this realistic). No warning is surfaced. This violates the durable-memory expectation.
  - Fix: Add a 'pinned'/importance field; never evict pinned or manual entries, and prefer evicting low-confidence auto-memory first. At minimum, evict by a combined score (age + inverse confidence) rather than age alone, and log evictions.
- **[medium/medium] Distillation pattern extraction is a hardcoded ~30-keyword web/devops allowlist, producing empty/garbage skills outside that domain**
  - Evidence: src/distillation/engine.ts:111-139 extractPatterns() only matches a fixed regex list: useMemo/useEffect, React/Vue, TypeScript/Python/Go/Rust, Docker/Kubernetes/AWS/GCP, REST/GraphQL, SQL/Redis/MongoDB, plus a few Chinese terms. Any domain not on the list (Bun, OpenCode, Postgres, Next.js, finance, data science, etc.) yields zero patterns. distillToSkill() (engine.ts:57) builds trigger = `When task involves: ${distillation.patternsLearned.join(', ')}`, which becomes 'When task involves: ' (empty) when no keyword hits, and buildSkillPrompt (engine.ts:141-154) emits an empty Key Patterns section.
  - User impact: Users distilling a real session into a reusable skill (hera_distill via evolution-tools.ts:137-139) get a skill whose trigger and patterns are empty or irrelevant, so it never fires or fires wrongly. The 'learn a skill from this session' feature quietly produces unusable output for most domains.
  - Fix: Replace the keyword allowlist with domain-agnostic extraction: pull capitalized/identifier tokens, file/tech nouns, or salient noun phrases; weight by frequency. Fall back to TF-style top terms so patternsLearned is never empty.
- **[medium/low] generateSummary is not a summary — just the first 5 assistant lines truncated, so it misses session outcomes**
  - Evidence: src/distillation/engine.ts:73-86 generateSummary() filters lines starting with 'assistant:' and takes assistantLines.slice(0,5), each truncated to MAX_SUMMARY_LENGTH. It only ever looks at the FIRST five assistant turns. In a long session the conclusion/decision typically lands in later turns, which are discarded. There is no scoring, no last-turn inclusion, no model-based summarization.
  - User impact: The distillation.summary stored to memory (engine.ts:39-45) and embedded into auto-generated skill descriptions (engine.ts:56) reflects the opening of the conversation, not what was actually decided or fixed. Recalled summaries mislead about the session's real result.
  - Fix: Include the final assistant turn(s) and any turns containing decision/fix markers, not just the first five; or label it 'session opening' rather than 'summary' if cheap heuristics are kept.
- **[medium/medium] Auto-memory regex extraction over-captures and assigns fixed fabricated confidence, polluting decision/fix stores**
  - Evidence: src/memory/smart-extractor.ts:36-49 captures `(.+?)` greedily up to the next punctuation after trigger words like 'should|must|need to … use|implement|apply'. Confidence is hardcoded (0.8/0.9/0.7 at lines 59/73/87) with no relation to actual match quality, and isValidMatch() (lines 105-109) only checks length 5..200. A casual line like 'you should use a clearer name here' is stored as a high-confidence 'decision', and 'I fixed the typo' becomes a 'fix' memory. These fabricated-confidence entries then drive recall ranking and survive eviction over real content.
  - User impact: With auto_memory enabled the decisions/fixes subdirs fill with trivial, decontextualized fragments (the trigger word is stripped, so context is lost). Recall surfaces noise and the confidence field cannot be trusted for ranking or filtering.
  - Fix: Require stronger signals (imperative + concrete object, code-fence proximity, or speaker = user) before extracting; store the surrounding sentence for context; derive confidence from match specificity rather than a constant.

### Cross-platform, security & error-handling robustness

- **[high/low] Skill subsystem accepts unvalidated names and file paths as filesystem path segments (traversal + arbitrary directory deletion)**
  - Evidence: Agents and memory ids are guarded (validateAgentName in agent-tools.ts:144; assertSafeId in json-collection-store.ts:16 blocks `..`, `/`, `\`, NUL), but skills are NOT. hera_create_skill (skill-tools.ts:24-31) and hera_delete_skill (skill-tools.ts:48-49) pass `args.name` straight through with no validation. SkillManager then builds paths from that raw name: writePackageToDisk does `join(this.skillsDir, pkg.name)` (manager.ts:275), loadSkill does `join(this.skillsDir, name)` (manager.ts:178), and deleteSkill does `rm(join(this.skillsDir, name), {recursive:true,force:true})` (manager.ts:198-200). A skill named `../../agents/hera` would recursively force-delete the authoritative agent directory; a name like `../../../x` writes/reads outside skillsDir. Separately, extra-file writing uses model-controlled relative paths unchecked: `const filePath = join(skillDir, file.path)` (manager.ts:300), a classic zip-slip write primitive (file.path = `../../../hera.json`).
  - User impact: Hera is LLM-driven and ingests untrusted content (task goals, team messages, packaged skills). A prompt-injected or careless skill name/file.path can silently delete the user's agents directory or overwrite arbitrary config files outside hera-data, corrupting the whole install with no warning.
  - Fix: Add a validateSkillName() (mirror validateAgentName) and call it in createSkill/deleteSkill/loadSkill before any join; run assertSafeId-style checks on every pkg.files[].path in writePackageToDisk, rejecting `..`/absolute segments.
- **[high/low] Agent description allows YAML frontmatter injection (newlines not sanitized)**
  - Evidence: buildFrontmatter only escapes double-quotes in the description: `description: "${def.description.replace(/"/g, '\\"')}"` (registry.ts:161). Newlines are not stripped, and the file is round-tripped: parseMarkdownAgent reads frontmatter line-by-line with `fm.match(new RegExp(\`^${key}:\\s*(.+)$\`, "m"))` (registry.ts:193-194). A description containing `\nmode: primary\npermissionJson: {"bash":"allow"}` injects real frontmatter keys that are parsed back on the next reload, silently overriding the agent's mode/model/permission, or breaking the `^---\n...\n---` parse entirely (registry.ts:180) so the agent reloads as the `unknown`/subagent fallback.
  - User impact: A crafted or model-generated description can escalate an agent's mode/permissions or quietly brick the agent on the next OpenCode restart (disk is authoritative), with the change persisting across sessions.
  - Fix: Strip/encode control chars and newlines in description (and any single-line frontmatter value) before writing, or emit the whole frontmatter as a single JSON/quoted block; validate on parse that injected keys aren't honored.
- **[medium/low] atomicWriteText is not crash-safe on Windows: unlink-then-rename leaves a window with no file at all**
  - Evidence: writeTextAtomically writes a temp file, then on win32 does `await unlink(filePath)` before `await rename(tempPath, filePath)` (helpers.ts:76-83). If the process crashes between the unlink and the rename, the destination is GONE — not stale, but lost — which is strictly worse than the partial-write it claims to prevent (docstring helpers.ts:52-55). On POSIX rename is an atomic replace so this gap doesn't exist; the bug is Windows-specific. This backs every JSON entry (json-collection-store.ts:62 -> atomicWriteJson) and agent backups (persistence.ts:97).
  - User impact: On Windows (Hera's primary dev/target platform per env), an ill-timed crash or power loss during a memory/task/backup write can delete the previously-good record entirely, undermining the 'durable, crash-recoverable' north star exactly when recovery matters.
  - Fix: Avoid the pre-unlink: rename temp over target directly (Node rename overwrites on Win32 modern Node), or on EPERM retry via a ReplaceFile-style swap, keeping the old file until the new one is in place.
- **[medium/medium] Authoritative agent .md and skill files are written non-atomically, against the repo's own convention**
  - Evidence: CLAUDE.md mandates atomicWriteText for 'persisted files that must survive interrupted writes', and the helper exists (helpers.ts:56). Yet the authoritative agent store uses raw writeFile: AgentRegistry.register (registry.ts:38), ensureHeraMd (registry.ts:120), appendEvolution (registry.ts:154). Skill packages likewise: SKILL.json/SKILL.md/config.json and extra files all via plain writeFile (manager.ts:287,290,294,303), as do package staging writes (package-tools.ts:253,263,289,405). Disk is documented as authoritative for agents (CLAUDE.md §2), so a half-written .md is the source of truth.
  - User impact: An interrupted write (crash, OOM, Ctrl-C) leaves a truncated agent .md; on restart OpenCode/parseMarkdownAgent loads garbage or the `unknown` fallback (registry.ts:181-188), silently degrading or losing the agent.
  - Fix: Route all agent/skill/package persistence through atomicWriteText/atomicWriteJson (after fixing the Windows gap above) instead of fs.writeFile.
- **[medium/medium] Acceptance evaluation runs unbounded regex and arbitrary shell with no schema constraint, able to wedge the supervisor**
  - Evidence: Acceptance checks are enqueued as `z.array(z.any())` (task-tools.ts:55), so command/pattern strings flow unvalidated from model output. AcceptanceEvaluator.regex compiles `new RegExp(check.pattern).test(source)` (acceptance.ts:87) with no length/complexity bound and no timeout — a catastrophic-backtracking pattern against large task output blocks the Node event loop (and thus the supervisor/loop tick, constants.ts:165,169). shell checks run `exec(check.command, ...)` with shellEnabled defaulting true (acceptance.ts:23,113), i.e. full shell-interpolation execution of whatever string the model placed in a task.
  - User impact: In a long-running 500-task engine, one bad acceptance regex from an LLM can silently freeze the whole supervisor (no crash for self-healing to catch), and the shell surface means a poisoned task definition runs arbitrary commands on the host.
  - Fix: Validate acceptance check shapes with a real zod schema (not z.any()); cap pattern length and run regex in a worker/with a deadline; gate shell checks behind an explicit allowlist or off-by-default config.
- **[low/low] Windows config-root fallback silently hardcodes C:/Users/Administrator**
  - Evidence: resolveOpenCodeConfigRoot, when USERPROFILE and HOME are both unset on win32, returns `join('C:/Users/Administrator', '.config', 'opencode')` (constants.ts:92-95). This is duplicated logic the CLI must mirror (CLAUDE.md path section).
  - User impact: In a service/CI/stripped-env Windows context the user's real profile env can be absent; Hera then reads/writes another user's profile path, producing permission errors or, worse, silently scribbling state into the Administrator account instead of failing loudly.
  - Fix: Throw a clear configuration error when no home/USERPROFILE/override is resolvable instead of inventing an Administrator path; keep the same behavior in bin/hera.js.
- **[low/low] deleteSkill reports success even when the on-disk removal fails**
  - Evidence: deleteSkill swallows the rm error (`catch { // ok }`) and unconditionally `return true` (manager.ts:199-204); the tool then prints `Skill "x" deleted.` (skill-tools.ts:50-51). If rm fails (file lock, EPERM, partial dir), the skill directory survives but the user is told it's gone, and it will reload on next init via readdir (manager.ts:133-146).
  - User impact: User believes a skill was removed, but it silently reappears after restart and may keep being embedded into agents — confusing, hard-to-diagnose 'zombie skill' behavior with no error surfaced.
  - Fix: Return false (and surface the error) when rm throws; only report deletion after confirming the directory is gone.

### Skills System + Export/Packaging

- **[high/high] Engine injection (withEngine) spawns competing engines on one shared dataDir → duplicate task execution, lost updates**
  - Evidence: Every generated plugin's bootstrap runs `createEngine({ dataDir: getHeraDataDir(), cwd: getHeraDataDir(), client })` then `engine.init()/recover()/start()` (plugin-generator.ts:199-203, team-plugin-generator.ts:207-211). OpenCode loads ALL plugins in one process, so if Hera and any generated agent/team plugin are installed in the same config root, each calls createEngine and gets its OWN in-memory TaskStore (index.ts:74) plus its own Supervisor + LoopManager loops (index.ts:88-99,129-132), all pointed at the same `hera-data` dir. claimReady selects from in-memory `byStatus("pending")` and writes with no disk re-read or atomic compare-and-set (task-store.ts:46-72); supervisor.recover() resets every running task whose lease expired regardless of leaseOwner (supervisor.ts:28,49 -> task-store.ts:74-88). Two engines therefore each see the task as pending in their own memory, both claim it, both execute, last writer wins. The default path makes this collision the norm: getHeraDataDir falls back to `~/.config/opencode/hera-data` (plugin-generator.ts:188-193).
  - User impact: The exact opposite of Hera's durable, no-double-work north star: co-installed generated agents/teams + Hera double-run the same tasks, clobber each other's task ledger writes, and run redundant supervisor/loop timers. At >=500 tasks this surfaces as duplicated side effects and corrupted task state.
  - Fix: Make the engine a process-wide singleton keyed by dataDir (registry/global), or skip createEngine in a generated plugin when a Hera engine is already present. Add a cross-owner guard: claimReady must reload from disk and refuse to claim tasks already leased by a live owner; recover() should respect owner liveness. Also fix `cwd: getHeraDataDir()` — running task/acceptance shell checks with cwd inside the data dir is the wrong working directory for real project work.
- **[high/low] Built-in skills can be silently shadowed by a disk package and then become permanently un-deletable**
  - Evidence: `hera_create_skill` accepts any name with no built-in guard (skill-tools.ts:25-31) and createSkill always writes a directory package to disk (manager.ts:155-172). On the next init, disk packages are loaded last and `this.loadedSkills.set(entry.name, packageToDefinition(pkg))` unconditionally overwrites the built-in entry placed earlier (manager.ts:115-117 vs 141). So creating a skill named `memory`, `caveman`, `evolution`, etc. replaces the built-in prompt that buildAgentPrompt embeds into every new agent. Worse, it can never be removed: deleteSkill returns false for any name where isBuiltin() is true (manager.ts:190-191, isBuiltin checks the static BUILTIN_SKILLS list at 223-225), so the on-disk shadow directory is orphaned forever.
  - User impact: A user (or an imported skill package) can override Hera's core skills, changing the behavior of every generated agent, and then has no supported way to undo it — `hera_delete_skill` refuses, leaving a stuck override that contradicts the documented 'built-in skills are non-deletable/canonical' guarantee.
  - Fix: Reject built-in names in createSkill (return an error), and in init() do not let a disk package overwrite a built-in entry (skip set when isBuiltin(entry.name)). Alternatively allow deleteSkill to remove a shadow directory whose name is built-in (delete the override, restore the built-in).
- **[medium/medium] Generated plugins read HERA_DIR, ignoring HERA_CONFIG_ROOT — the documented 'shared memory pool with Hera' is false under a custom config root**
  - Evidence: Generated memory/engine helpers resolve paths only from `process.env.HERA_DIR` (plugin-generator.ts:189,233; team-plugin-generator.ts:197,242), but Hera's runtime and CLI resolve the config root from `HERA_CONFIG_ROOT`/`OPENCODE_CONFIG_ROOT` (constants.ts:86-87, bin/hera.js:96). HERA_DIR and HERA_CONFIG_ROOT are different variables, so when a user sets HERA_CONFIG_ROOT=/custom (the canonical, documented override) but not HERA_DIR, Hera writes to /custom/hera-data while the generated plugin writes to `~/.config/opencode/hera-data`. Yet the generator's own comment asserts the tools 'read/write the same <configRoot>/hera-data/memory/ directory Hera itself uses, so generated agents share a memory pool with Hera' (plugin-generator.ts:152-156).
  - User impact: Any user with a non-default config root (HERA_CONFIG_ROOT) gets generated agents/teams that silently use a different memory pool AND a different engine task ledger than Hera — blackboard collaboration and engine continuity break with zero error, exactly the case the docs promise works.
  - Fix: In the generated helpers, honor HERA_CONFIG_ROOT (and OPENCODE_CONFIG_ROOT) before falling back to the home default, mirroring constants.ts precedence; treat HERA_DIR as a compatibility alias. Or have Hera inject the resolved absolute dataDir into the generated plugin at generation time instead of relying on env at runtime.
- **[medium/medium] includeMemory packaging selects memories by naive case-insensitive substring of agent name → sweeps unrelated/private memories**
  - Evidence: getAgentMemoryFiles flags a memory file for inclusion whenever `content.toLowerCase().includes(agentName.toLowerCase())` anywhere in the raw JSON (package-tools.ts:136). Onboarding seeds short agent names like `qa-engineer`/`senior-dev`, and users create names like `init`, `qa`, `dev` — `init` matches any memory containing 'initialize'/'initial', 'qa' matches 'equally'/'quality', etc. On unpack these files are copyDir-merged into the recipient's shared memory dir (package-tools.ts:410-416).
  - User impact: Packaging an agent 'with memory' to share/migrate can quietly bundle large numbers of unrelated memories (data bloat and a privacy leak of other agents'/sessions' content), and importing them pollutes the recipient's memory pool.
  - Fix: Match on structured fields (metadata.agent / owner / explicit agent tags) instead of substring over the whole file, or require word-boundary/exact match. At minimum scope to memory entries whose metadata references the agent, and report exactly which files are included before writing the archive.
- **[medium/medium] Skill package extra files are read/written as UTF-8 only, and file.path is not sanitized against traversal**
  - Evidence: writePackageToDisk writes each extra file via `writeFile(join(skillDir, file.path), file.content, 'utf-8')` with no check that file.path stays inside skillDir (manager.ts:300-303) — a package with `file.path = '../../evil'` escapes the skill directory. readPackageFromDisk reads every non-auto-generated file with `readFile(..., 'utf-8')` and stores it as a string (manager.ts:340-343); the `if (content !== undefined)` guard is dead because the `.catch(() => "")` already coerces failures to an empty string.
  - User impact: Skill packages that carry binary assets (images, compiled scripts, fonts) are silently corrupted on load (UTF-8 round-trip), and a crafted/imported skill package can write files outside its own directory, a path-traversal write primitive distinct from the tar-unpack path (which is guarded).
  - Fix: Validate/normalize file.path with the same isEntryInsideDir-style check before writing; detect binary files and store/round-trip them as base64 (or skip), and drop the dead undefined check.
- **[low/low] Unpack md-mode silently overwrites an existing agent with no backup or confirmation**
  - Evidence: hera_unpack_agent md branch does `writeFile(mdDest, content)` straight onto `<configRoot>/agents/hera/<agentName>.md` (package-tools.ts:399-406) with no existence check or backup, unlike persistence.ts which offers backupAgent/listBackups. Plugin-mode similarly copies into node_modules/<agentName> over whatever is there (package-tools.ts:384-391).
  - User impact: Importing a package whose agentName collides with an existing local agent destroys the local version with no recovery path, surprising a user who just wanted to 'try' a shared agent.
  - Fix: Before overwrite, detect an existing agent and either back it up (reuse persistence.backupAgent) or require an explicit overwrite flag, reporting the collision in the result.

## Appendix B — research feature ideas (2025-2026)

### Agent Memory & Knowledge Systems (state-of-the-art 2025–2026)

- **[high/medium] Hierarchical OS-style memory with self-editing memory blocks (MemGPT/Letta)** — Hera agents are persisted as Markdown bodies (buildAgentPrompt in src/agents/hera.ts) and Hera already injects a runtime prompt via the config hook. Today there is no tiered memory: MemoryStore is flat per-entry JSON with no notion of always-in-context 'core' facts vs. cold archival. Hera has the exact seams to add a tier model: a bounded, agent-editable core-memory block rendered into the agent prompt, backed by the existing MemoryStore as recall/archival. This directly serves the >=500-task durable north star because long-running agents need stable in-context identity/state that survives compaction.
  - Idea: Add a per-agent 'core memory block' tier: a small bounded section (e.g. <=2KB, validated via validation.ts) rendered into the agent prompt on every turn, mutated only through two new tools (hera_core_memory_append / hera_core_memory_replace) that persist through persistence.ts to all three layers. The session-compacting hook keeps the block verbatim (never summarized away), giving long-running agents durable identity/state across compactions.
- **[high/high] Temporal / bi-temporal knowledge-graph memory (Zep + Graphiti)** — Hera's MemoryStore writes one immutable-ish JSON per entry with no relations and no temporal validity — so a stale memory is just as retrievable as a current one, which is dangerous for long-horizon supervised execution. Hera does not need full Neo4j; the high-value, low-cost slice is bi-temporal metadata + lightweight entity linking on existing entries. This also fits teams' shared blackboard (hera_team_remember/recall), where conflicting facts from parallel agents need recency/validity arbitration.
  - Idea: Extend MemoryStore entry metadata with bi-temporal fields (event_time, ingest_time, invalid_at) plus an optional 'supersedes' pointer. When a new memory conflicts with an existing one (same entity+key), mark the old entry invalid rather than deleting it; retrieval defaults to currently-valid facts but can time-travel. No new DB — just metadata + an index file under hera-data/memory/.
- **[high/medium] Hybrid multi-signal retrieval (semantic + BM25 + entity fusion)** — This is Hera's biggest concrete gap: MemoryStore today has NO search at all — callers load entries by type/id from flat JSON. Adding any retrieval is strictly additive and unblocks every other memory feature (distillation, auto-memory, team recall). Because Hera runs in-process under Bun, a dependency-light hybrid index (BM25 over entry text + cosine over cached embeddings + metadata filter by type/agent/recency) is very achievable and avoids standing up a vector DB.
  - Idea: Add hera_memory_search: a hybrid retriever over MemoryStore combining BM25 (lexical) + optional embedding similarity + metadata filters (type, agent, recency, validity), fused and reranked, returning top-K with scores. Embeddings computed lazily and cached next to each JSON entry; pure-BM25 fallback when no embedding provider is configured so it degrades gracefully offline.
- **[high/medium] Memory consolidation & forgetting (episodic→semantic, dedup, decay)** — Hera already owns the perfect hook: experimental.session.compacting in src/index.ts runs the DistillationEngine and optional extractMemories() (auto_memory). But it currently extracts/distills without a consolidation pass — no dedup against existing memories, no episodic→semantic promotion, no decay/forgetting. For >=500-task durable runs this means unbounded, redundant, stale memory growth. The compaction relay (buildActiveWorkContext) is the natural place to consolidate episodic task traces into durable semantic lessons.
  - Idea: Add a consolidation pass to the session-compacting hook: before saving auto-memories, dedup/merge against existing entries (using the new hybrid search to find near-duplicates), promote repeated episodic observations into a single semantic memory, and attach a decay score (recency × access-count) so a future hera_memory_forget/prune job can retire low-value entries — with an audit trail so 'forgetting' is reversible and not catastrophic.
- **[medium/low] Memory evaluation harness (LongMemEval / LoCoMo / BEAM-style regression)** — Hera's north star is explicitly anti-'滥竽充数': no perfunctory completion, declarative acceptance checks in HDTE. That same philosophy should apply to memory — but Hera has no way to know whether a memory change improved or regressed recall. Tests live next to source under src/, so a memory-eval fixture fits the existing convention and would guard every change to the retrieval/consolidation features above (which otherwise risk silent ~20% fact loss).
  - Idea: Ship a small golden memory-eval fixture (a multi-session transcript + Q&A pairs covering single-hop, multi-hop, temporal, and knowledge-update cases) plus a bun test harness that runs Hera's ingest→consolidate→retrieve pipeline and asserts recall/precision thresholds — turning memory quality into a CI gate alongside the existing prepublishOnly checks.

Persist each agent's frequently-used domains in its .md so hot tools stay eager and cold ones defer. Measure token + acceptance-pass deltas across a 50-task batch.

### Multi-agent orchestration patterns (2025-2026)

- **[high/high] Plan-and-Execute with localized closed-loop re-planning (Planner-Critic-Executor / dynamic HTN)** — Hera already has every primitive but no closed loop connecting them: TaskStore has a real DAG (dependsOn), AcceptanceEvaluator IS a Critic, and LoopManager has an iterate-until-goal mode. What is missing is the Planner that turns a single high-level goal into a HDTE task DAG and, on an acceptance-check failure, re-plans only the failed sub-DAG instead of just retrying the same task. Today a failed acceptance check retries verbatim; the SOTA move is structured repair.
  - Idea: Add a 'planner' loop mode / hera_plan_goal tool: takes a goal, calls an agent to emit a TaskStore DAG (nodes + dependsOn), executes via the existing executor, and on AcceptanceEvaluator failure feeds the failure reason back to the planner to mutate only the failed subtree (insert remediation tasks, re-decompose) rather than retry-in-place. This directly serves the >=500-tasks-no-perfunctory north star by making the Critic drive structural repair.
- **[high/medium] Blackboard pull-based contribution / capability bidding (bMAS)** — Hera's blackboard (hera_team_remember/hera_team_recall) is currently push-style key/value storage for decisions/results; coordination still flows through the coordinator and inbox messages. Hera has the storage substrate and the 'adaptive' coordination mode but no open-call/claim semantics, so it cannot do self-selection or capability bidding.
  - Idea: Add open-call primitives on the blackboard: hera_team_post_request (coordinator posts a need + required capability tags) and hera_team_claim (an idle member atomically claims it, with a lease like TaskStore already uses). Match against the agent's declared skills. This turns the existing 'adaptive' mode into real dynamic team formation and removes the coordinator as a routing bottleneck.
- **[high/medium] Durable execution: graceful cooperative shutdown + checkpoint-on-signal (LangGraph)** — Hera's Supervisor does crash recovery via leases (recovers stuck/expired tasks), but there is no cooperative shutdown path: a SIGTERM mid-attempt relies on lease expiry and a later retry, which can re-run side-effectful work and burn an attempt. Hera also lacks time-travel/checkpoint-rollback over the task ledger.
  - Idea: Add cooperative graceful-shutdown to the engine: trap SIGTERM/SIGINT, stop dispatching new tasks, let in-flight attempts finish (or persist a partial checkpoint), flush TaskStore/LoopStore, and exit clean so restart resumes with zero lost or double-run work. Pair with a per-task 'checkpoint' field so a re-leased attempt resumes from last checkpoint instead of from scratch.
- **[medium/high] A2A protocol: Agent Cards + standardized Task lifecycle (Linux Foundation v1.0)** — Hera already EXPORTS agents/teams as standalone plugins and has a task lifecycle (pending/running/succeeded/failed/cancelled) that maps almost 1:1 onto A2A's states (note: A2A adds 'input-required', which Hera lacks and which is genuinely useful for human-in-the-loop). But exports are OpenCode-only and have no capability discovery surface, so a Hera-built agent cannot be discovered or driven by a non-OpenCode A2A client.
  - Idea: Emit an A2A Agent Card (.well-known/agent.json) during plugin/team export in src/generators: derive capabilities from the agent's skills, declare I/O modalities, and map HDTE TaskStatus onto the A2A task lifecycle (add an 'input-required' state to unlock human-in-the-loop). This makes exported Hera agents discoverable and drivable by the broader A2A ecosystem at low marginal cost.
- **[medium/medium] First-class handoffs + guardrails (OpenAI Agents SDK)** — Hera teams coordinate via inbox messages (hera_team_message) which are async notifications, not control transfers, and the receiving agent must reconstruct context manually. Hera has no explicit handoff primitive and no input/output guardrail gate at agent boundaries, even though its AcceptanceEvaluator is conceptually a guardrail living only at task-completion, not at handoff time.
  - Idea: Add hera_handoff(targetAgent, context): a one-way control transfer that packages the current active-work context (Hera already builds buildActiveWorkContext for compaction relay) and hands it to a peer, optionally running an AcceptanceEvaluator-style guardrail check on the handed-off payload before the target starts. Reuses the compaction-relay context builder as the handoff envelope.

### Context engineering for long-horizon agents (2025-2026)

- **[high/medium] Compaction + memory-tool as a measured economic lever (context editing)** — Hera already owns the OpenCode session-compacting hook (src/index.ts) with distillation + auto-memory extraction, and MemoryStore is effectively the same primitive as Claude's file-based memory tool. But Hera's compaction is monolithic 'distill + extract'; it has no notion of tiered eviction (clear stale tool results first, summarize only when that's insufficient). The 39% combined-lift result validates Hera's distillation+memory pairing but suggests it is under-exploiting the cheap tool-result-clearing tier.
  - Idea: Add a tiered compaction policy to the session-compacting hook: tier 1 = evict redundant/stale tool-result blocks (mirroring clear_tool_uses); tier 2 = distill remaining narrative; tier 3 = auto-extract durable memories. Record which tier fired and an estimated token-saved metric per compaction into MemoryStore so Hera can report a real 'tokens reclaimed' number and tune thresholds, instead of always running the full distill pass.
- **[high/medium] Cache-aware context management ('Don't Break the Cache')** — Direct hit on Hera's compaction relay. buildActiveWorkContext (src/engine/active-work.ts) builds a volatile 'Active durable work' block (live task/loop counts) that is injected into retained context. Whether that lands before or after the stable agent prompt determines whether Hera silently busts the prompt cache on every compaction. Hera also injects per-agent prompts live via the config hook (src/index.ts) and into generated plugins (withEngine) - all places where prompt layering order has real cost consequences across 500+ task runs.
  - Idea: Define a cache-aware prompt layout contract across all Hera injection paths: a stable, cache-eligible prefix (agent identity + skills + tool defs that do NOT change per turn) followed by a clearly delimited volatile suffix (active-work relay, just-in-time-retrieved memories, current goal). Guarantee buildActiveWorkContext output and distillation summaries are always appended as the volatile suffix, never spliced into the stable region, so compaction reuses rather than invalidates the cached prefix. Add a doctor/test check that asserts the static prefix is byte-stable across consecutive turns.
- **[high/medium] Sub-agent context isolation with condensed-summary handoff contracts** — Hera teams (src/team/) already spawn real isolated OpenCode sessions via client.session.create() with parallel/sequential/adaptive coordination - the isolation primitive exists. What's missing is an enforced condensed-summary return contract: today subagent results flow back via inbox messages (hera_team_message) and the shared blackboard (hera_team_remember) without a bounded-summary discipline, so a coordinator aggregating 500 tasks can re-accumulate exactly the context bloat isolation was meant to prevent. This is precisely the 'perfunctory completion at scale' failure mode in Hera's north star.
  - Idea: Add a structured 'task handoff summary' contract to team subagent completion: when a subagent finishes, require a bounded (~1-2k token) structured summary (outcome + artifacts-by-reference + acceptance-check evidence) that is what gets written to the blackboard / returned to the coordinator, while full transcript stays in the subagent's isolated session. Wire it into HDTE acceptance checks so a subagent cannot mark a task complete without producing the bounded evidence summary - directly fighting 滥竽充数 completion.
- **[medium/medium] Just-in-time retrieval / progressive disclosure via lightweight identifiers** — Hera's MemoryStore writes one JSON per entry under typed subdirectories - already an addressable, file-per-item store ideal for identifier-based retrieval. But the compaction/auto-memory path tends to push distilled content INTO context, and the active-work relay injects state eagerly. Hera lacks a JIT recall discipline where the engine keeps task handles (id + one-line + memory path) hot and the agent pulls full memory bodies only when a task is actually being worked. The HDTE task ledger (TaskStore) is the natural home for 'identifier-level' working memory.
  - Idea: Make the active-work relay identifier-first: instead of (or alongside) counts, inject a compact index of live tasks as {id, one-line goal, memory-pointer} handles, and expose a hera_recall_by_pointer tool so the agent fetches full task/memory bodies just-in-time only for the task it's executing. This keeps the retained-context block tiny across compaction while preserving full recall on demand, scaling cleanly to 500+ tasks.
- **[high/low] Context rot: length-driven degradation as a budget constraint (not a window-size problem)** — This is the mechanism behind Hera's stated 滥竽充数 / perfunctory-completion risk in long sessions: as a 500-task session fills past ~50%, the model recency-biases toward latest tool chatter and demotes the original acceptance criteria sitting early in context. Today Hera compacts reactively (on OpenCode's compacting hook) rather than proactively at a fill threshold, and crucially does not re-assert the goal/acceptance contract into the recency-favored tail after compaction.
  - Idea: Add a proactive context-budget watchdog to HDTE that estimates session fullness and triggers the compaction relay BEFORE the ~50% rot threshold, and - exploiting the post-50% recency bias defensively - re-injects each running task's goal + declarative acceptance checks into the freshly-retained tail on every compaction. This keeps the success criteria in the model's most-attended region precisely when long sessions are most prone to drift, hardening anti-perfunctory completion at scale.

### Durable Execution & Agent Reliability (2025-2026)

- **[high/high] Checkpoint-replay with step-level journaling & idempotency keys (not from-scratch resume)** — Hera's HDTE has a task ledger (TaskStore) + supervisor crash recovery, but recovery appears to operate at TASK granularity — a recovered task re-runs from its start, re-paying for already-completed LLM/tool work and risking duplicated side effects (double file writes, double messages). HDTE has no record of intra-task step outputs or idempotency guard. This is the single biggest gap between HDTE and 2026 durable-execution baseline, and it directly threatens the >=500-task-no-滥竽充数 north star: re-running expensive partial work on every crash makes long-horizon tasks economically and correctness-unsafe.
  - Idea: Add a step journal to TaskStore: a hera_step(taskId, stepId, fn) wrapper that, on first call, executes fn and persists its result keyed by (taskId, stepId); on replay after supervisor recovery it returns the journaled result without re-executing. Non-idempotent tool calls get an idempotency key = hash(taskId, stepId) passed to the tool. Supervisor recovery then resumes from the first un-journaled step instead of task start.
- **[high/high] Saga compensation / declarative rollback for failed long tasks** — HDTE's acceptance checks can REJECT a task as incomplete, but Hera has no concept of undoing the partial side effects an agent already committed (files created, messages posted, sub-agents spawned) before the rejection. On retry the agent re-runs over a dirty, half-mutated world — a prime source of perfunctory/incorrect 'completion'. Sagas give acceptance-check rejection a clean-slate guarantee.
  - Idea: Extend the task/step model so a step can register an optional compensate handler (e.g. hera_step(..., { compensate }) ). When an acceptance check fails or a task is aborted, the supervisor walks the journaled steps in reverse and invokes their compensators, recording compensation in the ledger, before re-queuing or marking failed. Surface a 'compensated' task state distinct from 'retrying'.
- **[high/medium] Agent SRE: circuit breakers + safety SLO + loop/spin detection** — HDTE has self-healing and a 4-mode loop engine (iterate-until-goal, scheduled-recurring, watch, drain-queue) — but an unbounded iterate-until-goal loop is EXACTLY the structure that can spin forever burning tokens without progress, which is the failure self-healing alone won't catch. There's no described per-task/per-agent circuit breaker or progress-SLO that trips after N failed iterations or stalled progress and quarantines the task instead of retrying blindly. At 500-task scale, one runaway loop can starve the executor.
  - Idea: Add a circuit breaker to the loop engine + executor: track consecutive-failure count and a progress signal (e.g. acceptance-score delta) per task; when failures exceed a threshold or progress stalls across K iterations, trip the breaker — move the task to a 'quarantined' state, stop scheduling it, emit a health event, and (in control mode) route to a human. Expose thresholds in hera.json with constants in src/constants.ts.
- **[high/medium] Durable human-in-the-loop interrupt / signal-based pause-resume** — Hera already has a 'control' team-management mode and inbox/blackboard channels, but a paused HDTE task that needs approval currently has no durable suspend-and-signal primitive — it would either block a worker or be lost on restart. Adding a durable interrupt makes the control mode actually durable and lets supervised long-running tasks gate risky steps (deploys, external posts) without holding executor capacity.
  - Idea: Add hera_task_await(taskId, prompt, options) that journals an 'awaiting-approval' checkpoint to TaskStore, frees the executor slot, and parks the task; resume it via an external signal — a new CLI command (node bin/hera.js approve <taskId> --decision approve|edit|reject) and an equivalent tool — that re-enqueues the task with the human's decision payload. Supervisor recovery must rehydrate parked tasks as still-waiting (never auto-fail them).
- **[medium/medium] Inspection/control protocol for in-flight durable tasks (agent-facing API, not just a dashboard)** — HDTE runs in-process inside OpenCode and its ledger is rich (tasks, acceptance checks, recovery state), but there's no described read/control surface for an external agent or supervisor to enumerate in-flight tasks, inspect their checkpoints/acceptance status, and intervene (pause, cancel, re-prioritize). Hera already exports agents/teams as standalone plugins and injects HDTE into them — those injected engines especially need a uniform inspection contract so a parent Hera can supervise child fleets toward the 500-task goal.
  - Idea: Expose HDTE as a small inspection/control tool group (and optionally an MCP surface): hera_task_list (filter by state), hera_task_inspect (steps journaled, acceptance results, breaker state), hera_task_intervene (pause/resume/cancel/reprioritize). Reuse the same contract in engine-injected generated plugins so a supervising Hera can drive child-plugin HDTE engines remotely.

### Agent Self-Improvement & Evaluation (2025-2026): reflective prompt optimization, LLM-as-judge eval, strategy memory / trajectory learning, agent eval harnesses, and automated agent design

- **[high/low] LLM-as-judge rubric acceptance checks (analytic rubric + CoT + bias controls)** — Hera's AcceptanceEvaluator (src/engine/acceptance.ts) currently supports ONLY deterministic check types: file_exists, regex, shell. There is a clean switch statement (the `one()` dispatcher) that is a perfect extension seam.
  - Idea: Add an `llm_judge` AcceptanceCheck type: { type:'llm_judge', rubric: Criterion[], threshold }. Reuse the existing AcceptanceEvaluator.evaluate loop and allPassed gate. This makes anti-perfunctory completion semantic, not just file/regex presence, and gives a human-readable 'why it failed' trail per task.
- **[high/medium] ReasoningBank-style strategy memory distilled from success AND failure trajectories** — Hera's DistillationEngine (src/distillation/engine.ts) is pure regex keyword extraction (it greps for 'React|useState|JWT' etc.), does NOT distinguish success from failure, and the distilled blob is never retrieved back into a future agent prompt. Meanwhile HDTE already records every task's outcome (completed/failed) plus acceptance results in TaskStore — Hera is sitting on labeled success/failure trajectories it currently throws away. - **[high/high] GEPA reflective prompt evolution (replace regex evolution with trace-driven Pareto search)** — Hera's evolution is proposeEvolution() in src/evolution/auto-evolve.ts — a hardcoded list of 7 regex→canned-directive pairs (SQL injection, null pointer, race condition...). It is brittle, never measured, and cannot discover anything not pre-baked. But Hera already has the two things GEPA needs: (1) a mutable text artifact — the persisted agent .md body via persistAgent()/buildAgentPrompt(); (2) a per-run metric + textual feedback — the new llm_judge/acceptance results from the task ledger. The evolution-tools domain is the natural home.

Keep human-in-the-loop: propose, don't auto-apply (consistent with current evolution policy).
- **[high/medium] Reproducible agent eval harness + pass^k reliability gate (a 'tau-bench for your own agents')** — Hera has NO eval harness today and the CLAUDE.md prepublishOnly gate is purely typecheck/lint/test/pack — there is no behavioral regression test that an exported agent/team still works. An eval harness closes the loop for both LLM-as-judge and GEPA above — all three concepts share the same scenario+rubric substrate.

Strictly proposal-mode with an approval gate before any candidate is persisted/exported. Start narrow: search over team rosters/modes for the seeded dev-team rather than free-form code.
